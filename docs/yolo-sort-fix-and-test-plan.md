## 3. 核心数据契约

统一检测记录：`bbox_xyxy`（原图坐标浮点值）、`class_id`、`class_name`、`confidence`、`detection_index`。这些字段必须来自同一次前向及后处理。

统一跟踪记录：检测记录的相关字段，加`local_track_id`、确认状态和本次匹配关系。类别和分数取本次匹配检测；不按返回数组位置拼接分数，不从另一轮推理获取属性。

- 内部优先使用具名记录，避免把字符串和数字混入NumPy数组后全部转成字符串。
- 空框数组规范为`(0,4)`；旧跟踪接口的空输出与非空输出列数一致。
- 原图坐标保持浮点，绘图/展示时再取整；消息分数保留原始精度，界面显示可保留两位小数。
- 保留已有JSON字段videoId、objectID、objectDetect、score、position等，新增protocolVersion、sessionId、eventId、时间语义等字段采用向后兼容方式。
- JSON objectID建议为`sessionId:localTrackId`，仍为字符串；画面可显示简短本地ID。服务或摄像头任务重启后，不与旧会话复用同一个业务ID。

## 4. 逐项修复设计与验收

### F1：分数与目标错配

将ui.py两轮检测合为一轮；SORT在匹配时同步接收并返回该检测的类别和分数。图上标注、录像标注和JSON统一消费同一条跟踪记录。

验收：输入工人0.43、牛0.91，任意交换检测顺序或轨迹输出顺序，都仍然各自匹配正确；仅一个目标已经确认时，也不取未确认目标的分数。0.699与0.700等边界值按原始分数分级，显示取整不改变计算结果。

### F2/F11：空帧推进与空输入

每次成功读取视频帧都调用一次跟踪更新，即使检测列表为空。输入侧统一规范形状，验证框、类别及分数数量一致；空输出有明确结构。

验收：保留max_age=1时，一帧漏检保留内部轨迹，两帧连续漏检删除；100帧空检测后同位置新目标不会继承旧ID。全程空视频、首帧空、已有轨迹后的空帧均不抛异常。

这里“每帧”指当前管线成功读取并处理的帧。本轮不引入主动丢帧策略；后续若采用最新帧队列，需要同时调整运动模型的时间步，不能直接沿用固定dt的假设。

### F4：退化/非法框

坐标还原和边界裁剪后，检查形状、有限值、x2>x1、y2>y1；仅过滤无效条目。进入卡尔曼前再做防御性校验，对NaN/Inf轨迹统一清除并保持轨迹与预测数组索引一致。

验收：零宽、零高、反向坐标、NaN、Inf、完全位于padding内的框不会进入卡尔曼；与它们同帧的合法目标仍正常处理。

### F6：类别永久锁死

本轮采用确定且容易验证的策略：匹配成功时，类别与置信度一起更新为当前检测结果；轨迹初始类别不再永久锁定。

验收：首次balloon、后续持续worker时，输出类别可更新为worker且分数对应worker。前端聚合类别变化时，同步使用该类别对应的分数统计，不能套用另一个类别的历史最高分。

这是类别纠错，不是新增跨帧分类器。类别抖动、纯IoU关联的交叉换ID仍需后续评估。暂不加入未经验证的类别硬门控或投票阈值，以免阻止纠错或引入更多ID切换。

### F8：轨迹确认与短暂漏检恢复

将min_hits定义为新轨迹所需的连续有效检测次数，包含首次创建，使用达到阈值的判断。默认仍为5，因此第5次连续检测首次输出。确认后使用独立confirmed状态，在max_age允许的短暂漏检内恢复匹配，无需重新等待5次。

验收：第1至4次不输出，第5次输出；已确认目标漏检1帧后恢复，首次匹配即可输出同ID；漏检2帧删除，再出现时分配新ID并重新确认。

漏检期间默认不把纯预测框当成新的有效告警输出，避免“没有检测却声称检测到目标”。

### F9：重复前向和无效分配

建立单一检测入口，移除每帧被立即覆盖的零张量分配；predict和detect_bounding_box如保留，则作为兼容包装，主视频循环只调用一次检测入口。兼容现有Torch版本使用no_grad上下文，不以缺少它作为已证明显存泄漏的依据。

验收：N个成功处理帧，对应N次前向和N次NMS，与是否检测到目标无关。统一坐标和分数流程与原单次YOLO结果一致，允许坐标显示取整造成不超过1像素的差异。

### F3：共享YOLO模型并发

第一轮采用单个模型加推理互斥锁；保护模型初始化、必要预热以及前向中grid/anchor_grid缓存的使用。等待锁时能检查任务停止信号。解码、绘制和跟踪等任务局部工作尽量放在锁外。

不复制整模型到每个摄像头，不修改checkpoint的模块路径或网络结构。串行保护首先保证正确性，多路吞吐之后再测量评估。

验收：多线程混合横屏、竖屏、方形输入，无尺寸不匹配错误；受控交错测试中同一模型同时进入forward的数量最大为1。每路结果与同输入单线程参考结果对应，任务间不串框。

### F5：任务去重、停止和会话

使用带锁任务注册表，以videoId标识同一摄像头运行任务；状态至少包括STARTING、RUNNING、STOPPING、STOPPED、FAILED。运行中相同摄像头、相同URL的启动请求返回现有会话；不同URL明确报告冲突，不悄悄启动第二个任务。

控制协议建议：action=start/stop/heartbeat，附videoId、clientId、requestId及必要的sessionId；通过任务状态消息确认结果。原有不带action的消息按启动请求兼容处理，仍按videoId去重。

- 前端添加后登记持有者；移除、替换、缩小布局、离开页面都释放当前持有者。
- 多浏览器可共享一个摄像头任务，按clientId登记持有者；一方退出不停止另一方仍在使用的任务。
- 默认心跳5秒，租约20秒，均可配置；异常关闭页面由租约回收，避免依赖卸载消息必达。旧协议不具备心跳，作为legacy持有者处理，可通过显式stop停止，不伪装为支持自动回收。
- 读流设置5秒级可配置超时；先验证现有OpenCV/FFmpeg后端支持情况。若阻塞读取无法获得可靠超时，采集改为可终止的独立进程，不用强制终止Python线程。
- 旧任务结束时，只能移除仍指向自己的注册项，防止误删新任务。
- 录像目录/文件名包含sessionId，避免同时写同名文件。任务数上限配置化，初始建议9，与界面最大布局匹配；这不表示CPU能让9路均达到实时帧率。

验收：同摄像头重复/并发启动只有一个任务；重复停止幂等；两个持有者退出一个仍运行，最后一个退出后停止。正常停止应在一个当前操作周期内完成，网络阻塞的退出上界按读超时、当前单帧推理时间及不超过2秒清理余量计算；租约回收另加租约等待时间。

### F7：异常清理与重试

任务入口统一校验消息并捕获异常；cap、writer、任务登记和未发状态等在finally中清理。异常进入FAILED并可见，重新启动生成新会话。将模块导入与服务启动分开，使测试可以导入业务代码而不自动连接MQTT或开启永久循环。

验收：在打开视频、推理、写视频、编码、发布等节点注入异常，资源均释放、登记均回收；相同摄像头可以重新启动；正常结束和stop路径不丢失应关闭的录像尾部。

### F10：时间语义

- 新协议传ISO8601带时区时间，内部采用带时区时间对象；界面统一按Asia/Shanghai展示。
- 为当前前端旧格式消息做明确兼容：已知toISOString截断的旧格式按UTC解析，并记录兼容路径；无来源的无时区输入不再靠猜测，按明确配置或拒绝处理。
- 离线文件以媒体PTS为优先，无有效PTS时按起始时间及帧序号/FPS计算。慢速推理不改变视频时间轴。
- RTSP没有可靠源PTS/采集时间时，标为帧接收时间；不能把它宣称成摄像机采集时间。处理完成时间单独记录。
- 与现有后端LocalDateTime接口交互时，在统一适配层按已有DTO格式转换上海当地时间，避免把带Z字符串当成本地时间；数据库字段本轮不迁移。

验收：已知UTC15:00在上海显示23:00；跨日正确；25FPS文件第250帧时刻相对首帧为10秒（按从0开始计数），人为增加处理等待不改变该时刻。

### F12：持续目标时告警延迟和消息积压（本次复核新增，待复现）

代码依据：ui.py在result非空时写出并清空image_queue；但Message_queue发送依赖image_queue达到save_num且flag非零。持续每帧有已确认目标时，图像队列可能一直达不到该门槛，消息不断累积到目标消失一段时间或视频结束才发送。

执行时先建立连续目标用例验证该推导。若复现，告警发送与录像缓存解耦：新轨迹确认事件立即发送，已有轨迹更新合并并默认最多每秒一次，图片独立限频；录像缓存只决定录像片段。

待发队列必须有数量/容量上限；同轨迹普通状态更新可合并，新增/结束事件不静默丢弃。发布失败或队列满必须进入明确的重试、背压或任务失败状态，测试中验证所选策略。建议首版数量上限256条，更新同轨迹合并；关键事件无法入队时明确报错并结束当前任务，避免无界占用内存。

验收：Broker正常时，从轨迹确认到告警被测试订阅者收到不超过1秒；连续300个有效目标帧不等待EOF才发消息；消息队列有界，录像仍可读；Broker断开时不会无界积压。

### 单元与故障注入

Python优先使用标准库unittest/mock与现有NumPy、FilterPy；检测器、读流、录像、发布和时钟可注入。测试不自动连接真实设备或现有Broker。前端抽离控制/聚合逻辑，结合现有TypeScript工具做断言、类型检查及浏览器回归；如需新增测试依赖，只加入开发依赖并记录版本。

T08除普通压力循环外必须保留确定性线程交错用例，防止因“恰好没撞上”而误判。T11/T13不只检查日志，还检查资源释放次数、注册表、队列及收到的消息。

### 离线真实模型

使用best1030.pt和现有smoke-cow-short.mp4等固定样例。修复前后记录同一输入、同一权重、同一阈值下的原始检测输出。验证新管线等价于原单次推理结果，变化主要来自跟踪状态和属性修正。

记录单路端到端耗时、前向次数、峰值RSS；GPU可用时额外记录显存，不把GPU缺席当成CPU测试失败。固定样例没有完整标注，因此不能据此声称mAP提升或召回率提高。

### 隔离联调

- 用本地视频循环发布测试RTSP，覆盖横屏和竖屏。
- 用独立Broker/主题前缀、临时录像目录及模拟告警API验证；需要真实数据库验证时使用独立测试库和合成记录。
- 对1/4/9布局及添加、移除、替换、缩小布局、离开页面做控制协议回归；9路控制用例可用模拟推理，真实权重先测1/2/4路并报告容量。
- 完成一次4路5分钟的真实权重循环稳定性验证，观察线程/队列/内存趋势，结束后确认资源回收。后续仅在代码变化或失败有必要时重跑相关测试。
