# 第六课 · 一张花屏图为什么能报出“风筝 0.73”？检测开启后究竟存什么？

回想你发过的第二张截图：图的上部还能辨认，下面大片像素拉成竖条，中间却画了一个红框，写着 `kite 0.73`。面试官问“你怎么知道问题出在传输”“当时模型究竟看到了什么”时，这张图是起点。它说明系统生成过这份证据。要找原因，还得沿着图像产生的路径逐段取证。

建议分两次读。第一遍约 20 分钟，读第 1～3 节，能解释一帧损坏为什么会影响一次风险判定。第二遍约 20 分钟，读第 4～6 节，自己挑选证据、算一次录像预算，再做文末实验。你负责算法和告警传递，前端只需掌握一件事：用户看到的框怎样对应到当时那一帧。

## 1. 从一张 JPEG 往前追，最先坏的是哪一段？

先在纸上画两行。上面一行写“视频源 → MediaMTX 转发 → 算法端解码 → 模型推理”。下面一行从推理结果画两条箭头，一条到“轨迹观测 → MQTT → 后端”，另一条到“证据截图 → 图片上传”。牛框和风筝框是在推理之后才出现的；画面像素在此之前就要先经解码。第五课里重发一条观测消息，可以找回未确认的业务结果，却不能修复先前已经损坏的像素。[观测与截图的生成顺序](../RailwayDetector/track_events.py) · [截图编码与上传](../RailwayDetector/evidence_outbox.py)

**补三个词。** H.264 是本次视频使用的压缩编码。它可以利用前后画面的相似之处，只保存还原图像所需的信息。**关键帧**为解码提供重新建立画面的起点，数据量可能比普通帧大。**解码**就是把压缩数据还原成模型可用的像素。遇到缺失或损坏的数据，解码器有时仍能给出一张尺寸正确的图，其中部分像素是它为维持播放而补偿出来的。一个 0.73 的检测分数只描述模型对这些输入像素的预测，不能替画面质量作证。

排障时每做一次对照，只回答一个问题。下面是项目保留下来的实验记录。

| 问题 | 怎么查 | 证据支持的结论 |
| --- | --- | --- |
| 截图发生在修复前还是修复后？ | 第二张图与业务证据文件匹配，采集于北京时间 12:13:56，当天队列调整是 12:52 | 这张图记录的是修复前的故障。第一张图没有唯一匹配，时间仍未知。[排查记录](frame-quality-findings-2026-11-11.md) |
| 输入文件本身已损坏吗？ | 用严格解码器完整读取原文件，再读已知损坏录像 | 原文件 373 帧通过。损坏录像前 71 帧可以交付，随后被拒绝。只抽第一帧会漏掉故障。[整段解码结果](test-results/frame-quality-2026-11-11/full-decode-result.json) |
| 转发设置会改变结果吗？ | 固定源和 MediaMTX 1.18.2，比较写队列 512 与 8192。两组都成功录下文件，再严格解码录下的内容 | 小队列组严格解码失败，大队列组通过。结果支持高码率关键帧突发超过原队列承载能力的解释。没有逐包追踪到某个包被丢的确切位置。[对照数据](test-results/p1-completion-2026-11-11/media-queue-comparison.json) · [变量与实验条件](p1-completion-results-2026-11-11.md) |

这里有两个不同的修复点。把转发写队列调到 8192，解决了此样例可复现的输入损坏；在算法入口加入严格解码，是为了将以后仍能检测到的损坏隔离在模型之前。队列大小指转发写队列的配置值，不能读作“允许模型积压 8192 张图”。增加转发缓冲还会占用更多内存，上线到别的码率、相机与读者数量时仍需验证。[部署配置](../deploy/compose.yaml)

## 2. 沿代码走一次：坏包怎样被挡在模型前面？

打开 `video_capture.py` 的 `_reader_main`。程序先识别视频地址类型。RTSP 直播进入独立解码进程里的 `StrictCapture`，普通本地文件读取路径使用 OpenCV。前面的整段文件验证是主动用严格解码器作检查。以下跟的是**实时检测路径**。[直播入口与进程间传递](../RailwayDetector/video_capture.py)

**第一步，加入正在播放的视频。** 刚接上时可能正处在一组相互依赖的画面中间。程序要求用 TCP 拉取 RTSP，设置 FFmpeg 的 `err_detect='explode'`，捕捉原生错误，并从 `waiting_keyframe=True` 开始。启动时先等关键包，再等可用的解码关键帧。若此时发现损坏，`_reject()` 会清理解码缓冲和待交付帧，回到等待干净起点的状态。此时跟踪器尚未得到这批像素。[StrictCapture 初始化与 _reject](../RailwayDetector/strict_capture.py)

**第二步，对比两个长得很像的分支。** 下面是 `read()` 从待交付帧中取出一个候选时的原代码片段。读到 `continue` 时，想一下调用者究竟有没有拿到图。

```python
if frame.is_corrupt:
    self._reject();continue
if self.waiting_keyframe:
    if not frame.key_frame:continue
    self.waiting_keyframe=False
```

1. 启动时遇到一帧没有损坏标志、但也不是关键帧的图，执行 `continue`，在解码器内部继续等待。模型调用次数没有增加。
2. 已经稳定出图后，若新帧带有损坏标志，则进入 `_reject()`。这时等待标志已关闭，函数会抛出 `FrameDecodeError`，控制流不会走到图像返回处。
3. 如果损坏标志是 False，但 `packet.decode()` 抛出解码异常或 FFmpeg 报了错误日志，项目也进入拒绝分支。检查覆盖包、解码结果、异步错误以及像素转换。只有通过相应检查才可能 `return True, image`。镜头本身脏污、画面被挡住、源头已经把坏画面编码成合法视频等问题，仍可能通过这些检查。[完整 read 路径](../RailwayDetector/strict_capture.py)

**第三步，把错误送回算法任务。** 直播解码循环把 `FrameDecodeError` 转成进程间的 `decode_error` 消息。父进程的 `BoundedCapture._receive` 识别它，重新抛出类型明确的异常。这个步骤解释了一个很实际的问题：子进程知道画面坏了，若父进程只收到“没拿到图”，上层就会丢失这个判断依据。连接重置、特定传输超时则可以归为源不可用。[子进程与父进程的错误映射](../RailwayDetector/video_capture.py)

**第四步，看异常跨过了哪一行。** 在 `ui.make_result` 里，先 `ok, frame = cap.read()`，后面才有 `observations, results = process_frame(...)`。第一行抛出解码错误时，这一次根本到不了推理。外层记录 `sourceQuality='CORRUPT'`，并在收尾时让已上报的活动轨迹发出 `INTERRUPTED`。第五课的持久队列承接这条状态消息。若终态本身写盘失败，代码会报告错误，之前已写入的消息仍然保留。[任务主循环与 finally](../RailwayDetector/ui.py)

到这里，把同一头已经确认的牛放进三个场景：

| 此刻得到的输入 | 模型与跟踪器本次怎样走 | 能告诉第四课的风险逻辑什么 |
| --- | --- | --- |
| 图片有效，模型输出空列表 | 推理已完成，跟踪器收到一次没有检测框的有效观测 | 原轨迹可进入 `MISSING`。恢复匹配可以续接，后续有足够有效缺失证据才可能解除。 |
| 已稳定出图后，本帧解码报损坏 | 这次推理不执行，已有活动轨迹随任务中断收尾 | `INTERRUPTED` 表示失去观察条件。没有证据表明牛已经离开。 |
| 图片有效，但牛被另一物体遮住，模型依然输出了一个相似框 | 当前帧正常进入 SORT，有可能发生第三课讲过的错误关联 | 解码检查只能证明通过了码流检查。判断认错目标，需要看这次处理的图、框及编号。 |

<details>
<summary>进阶追问 · 为什么队列一处加大，另一处却只保留最新帧？</summary>

MediaMTX 写队列位于解码前，装的是待发送的流数据，突发时缺了后续解码依赖的数据可能破坏画面。算法的最新帧缓冲位于解码后，装的是已经能独立使用的像素图。`_latest_loop` 持续解码，慢消费者下一次取最新完整帧，记录跳过了几帧。这样保住画面新鲜度，代价是快速经过的目标可能落在两个推理时刻之间。这两处队列的内容、目的和丢弃后果都不同。

若连解码本身都在落后，代码还比较“本次连接以来经过的实际时间”和“媒体时间前进了多少”。相对积压增长默认超过 2 秒会中断并要求重连。这个指标能发现持续落后，无法量出接入之前已经存在的固定延迟。[最新帧缓冲](../RailwayDetector/video_capture.py) · [相对积压计算](../RailwayDetector/strict_capture.py)

</details>

## 3. 怎样向面试官证明这两处改动各自有效？

上游看固定输入的队列对照，下游看损坏到来后**模型调用次数与最终轨迹状态**。如果只展示“改完之后预览正常”，这两件事其实都没验证充分。

项目曾对同一 4K 样例的直播转发跑过一次 65.296 秒探针。解码了 1,535 帧，模拟慢消费者读取 197 帧，另外 1,338 帧为取最新帧而跳过。该次解码错误数为 0，抽查 50 帧与原文件参考图的像素平均绝对误差（MAE）为 0。可以当场做一个校验：197 + 1,338 = 1,535。“跳过很多”与“没有发现解码错误”可以同时成立。这里 197 是消费者读图数，把它当作模型推理次数或现场识别准确率都会改变实验口径。[历史探针原始结果](test-results/frame-quality-2026-11-11/strict-probe-result.json)

独立的业务用例则在第 9 次读取注入解码错误。假摄像头前 8 次都提供有效画面，模型持续报告一个目标。测试检查 `model.calls == 8`、最后一条轨迹消息为 `INTERRUPTED`、源质量为 `CORRUPT`。若有人以后把读帧异常改成返回空检测列表，只看“进程没崩”的用例可能仍会通过，这条测试能捕捉行为回退。[损坏输入不进入模型的测试](../RailwayDetector/tests/test_worker.py)

## 4. 实时检测开着，到底哪些结果一直存？

面试时先明确对方想查什么，再说对应数据的位置和保留方式。举个例子，系统已经处理过一帧，值守人员十分钟后才来查。能否找回它，取决于当时哪条路径留下了证据。

| 对方想查什么 | 项目实际留下什么 | 查询的边界 |
| --- | --- | --- |
| 这一秒模型刚看到了什么？ | 完整解码帧和单帧检测先存在内存。实时检测视图用同次推理的缩小图、框、类别、当前分数与可选跟踪 ID。每路仅保留最新可用结果，默认最多推送 2 次/秒。 | 等待、过期、源异常和“有效帧上对象列表为空”含义不同。最新图会被替换。 |
| 后端是否处理过这条轨迹消息？ | 确认轨迹在首次出现、状态或类别变化以及持续期间间隔上报快照。成功写入 SQLite 待发后传给后端，MySQL 保存接收记录、轨迹状态与业务事件。 | 稳定可见时快照通常约每秒一次。SQLite 经确认可释放待发，后端接收记录仍可查。关系库没有每个源帧的完整图像和所有历史框。 |
| 某次告警当时有可看的静态证据吗？ | 活动轨迹的截图把对应框、类别、分数画进缩小的 JPEG，以消息 ID 关联，走独立图片待发。源轨迹截图有 2 秒节流，服务端每起事件最多接收 3 张。 | JPEG 里画上的框已成为像素，不能像叠加图层那样单独关闭。达到上限或上传失败，媒体和关键事件要分别查。 |
| 两次模型采样之间，牛或飞鸟实际怎样移动？ | `FULL_SOURCE` 用独立 FFmpeg 拉流，复制源视频码流到分段文件，目标段长约 30 秒。文件闭合后登记时段、会话和摘要。 | 能看已录下的源画面，但独立拉流可能有自己的起始时刻、损坏或缺口。登记时间是录制端估计，无法据此逐帧贴回算法框。 |
| 模型在已归档的某个采样时刻，给谁画了什么框？ | `DETECTION_SAMPLES` 保留同次推理图像的采样录像和配套 JSON。出现检测对象时包含前后约 2 秒及持续期间，默认最多 2 FPS，约 30 秒切段。 | 注重可复核的采样。长时间空场景通常不会新建采样片段，也可能因预算或编码队列少留画面。 |

对应入口是[实时结果](../RailwayDetector/detection_views.py)、[关键观测](../RailwayDetector/track_events.py)、[截图上传](../RailwayDetector/evidence_outbox.py)、[原始录像](../RailwayDetector/source_recording.py)与[采样录像](../RailwayDetector/analysis_recording.py)。

**走一次分流的代码。** `make_result` 得到 `observations`（单帧检测）和 `results`（已确认的匹配轨迹）后，先 `events.update(...)`。当有快照要发时，`TrackEvents._send` 先完成持久交接，再尝试截图。随后主循环才调 `result_frames.build(frame, observations, results, ...)`。它把同一张图和这一帧的检测放在一起，按照 `detection_index` 给已确认的框附上轨迹编号。未确认的框也可以显示，只是 `trackId` 为空。实时视图与采样录像共用这份结果，无需为了展示再跑一遍模型。媒体分支失败时，已经交接的关键观测仍然存在。[任务分流](../RailwayDetector/ui.py) · [ResultFrames.build](../RailwayDetector/detection_views.py)

## 5. 为什么采样录像能开关框？为什么两段录像不能直接对齐？

假设模型实际处理并采样了三张图，它们距片段开头分别为 0、0.75、2.25 秒。若把三张图当作 30 FPS 的连续三帧播放，第三张在约 0.067 秒就会出现，原本持续两秒多的运动会突然快进。项目允许采样帧之间间隔不同，叫**可变帧率（VFR）**。PTS 是帧应该呈现的时间戳，乘以时间单位 `time_base` 就是相对播放时间。[PyAV 对帧时间的定义](https://pyav.org/docs/stable/api/frame.html)

沿 `AnalysisRecorder._append` 看三步。下面摘出给视频帧和结果记录写时间的核心语句。[采样写入与闭合](../RailwayDetector/analysis_recording.py)

```python
offset = round((datetime.fromisoformat(metadata['observedAt']).timestamp() - self.started) * 1000)
# 创建待编码的视频帧后，记录它在片段里的毫秒位置
frame.pts = offset
frame.time_base = Fraction(1, 1000)
# 同一帧的框、类别、轨迹和帧号已加入对应的结果记录
self.entries[-1]['offsetMs'] = offset
```

1. 从当时的观测时间计算相对片段开始的毫秒差，示例得到 0、750、2250。
2. 视频帧的呈现时间和配套 JSON 的 `offsetMs` 使用同一个数。已读到的画面和它的检测结果因此有共同依据。采样间隔超过 3 秒或时间不再递增时，程序结束旧段并清空之前的预留帧。
3. 播放器用浏览器实际呈现帧的 `mediaTime` 选择这一帧的框。暂停或跳转后，框仍跟对应的采样图走。关闭框只隐藏新增的图层；源里已经烧入的标注或截图里的红框仍在。原录像使用另一条拉流连接和估计时钟，缺少这种同帧关系。[播放器取帧](../web-vue/src/components/RecordingPlayer/index.vue)

真实验收里有一段 46 帧、30.265 秒的采样录像，验证了视频 PTS 与配套记录对应。另有真实浏览器播放、跳转与开关框的历史结果。需要复盘“模型当时怎么看”时优先找这份同次推理采样。若只留了原录像，可以事后重新推理，但应将结果标成后来重算的结果。[采样解码记录](test-results/frame-quality-2026-11-11/sample-decode.json) · [浏览器记录](test-results/frame-quality-2026-11-11/browser-result.json)

<details>
<summary>进阶追问 · 有 30 天留存和 2 TB 预算，能保证存满一个月吗？</summary>

先问所有摄像头要连续保存的**总码率**。用十进制计量，30 天有 2,592,000 秒。2 TB 的理论上限是 `2 × 10¹² × 8 ÷ 2,592,000 ≈ 6.17 Mbit/s`，还要扣除媒体开销和其他占用。已测 4K 样例单路约 13.18 Mbit/s，连续录 30 天约需 4.27 TB。配置的 2 TB 是应用预算，实际可用磁盘也会先成为约束。

项目为截图和磁盘剩余空间预留预算。预算不足时会报告录像受限，不能靠提前删除未过期证据腾空间。30 天适用于配置的媒体保留策略，不能推断所有 MySQL 接收记录与审计表也会自动在第 30 天清除。答“会一直存吗”时还应说明，只要任务在运行，持续目标仍产生新观测，关系库增长需要单独规划。[媒体预算实现](../RailwayDetector/media_budget.py) · [容量核算与限制](p1-completion-results-2026-11-11.md)

</details>

```bash
  RailwayDetector.tests.test_detection_views.ViewTests.test_vfr_video_has_exact_sample_pts_and_real_elapsed_duration
```

第一个用例注入原生错误日志，断言抛出 `FrameDecodeError`。第二个断言模型只被调用 8 次，并检查最后的轨迹消息。第三个用例在临时目录里真正编码并重新解码 MP4，逐帧检查 0、0.75、2.25 秒，核对 JSON 里的三个偏移；末帧还留 0.5 秒显示，所以总时长为 2.75 秒。三种测试分别回答“入口能否识别错误”“业务有没有误判”“存下来的画面能否对齐”。[解码测试](../RailwayDetector/tests/test_strict_capture.py) · [采样回放测试](../RailwayDetector/tests/test_detection_views.py)

**实验 B · 选择下一份证据。** 假设告警截图拉丝，原录像中同一时段看起来正常。先对摄像头、会话和时间范围，再找是否有相应的检测采样。若同次推理的采样也花屏，应往算法输入、转发与解码记录查。若能匹配到同一处理帧且采样清晰、只有截图异常，再优先查截图生成、编码与展示。若根本没有相应采样，结论只能停在“存在差异，缺少同帧证据”。重新截一张相邻时刻的正常画面，无法解决这个证据缺口。

**面试口述。** “我们遇到过一张花屏图被识别为风筝。先把截图对到采集时刻，再比对原文件和转发后录像的整段解码。在同一源和同一转发器版本下，写队列 512 能复现，调到 8192 后这组样例通过了。算法端另加严格解码，运行中遇到可检测的损坏就中断观测，不让它贡献一次空检测。复盘时用原录像查连续运动，用同次推理采样查模型当时的框，用接收记录查后端处理结果。每一种证据只能回答对应的问题。”

**合上讲义，试着用自己的话答三题。**

1. 摄像头昨天拍到牛。今天遇到两次“没有牛框”，第一次画面清晰、模型输出为空，第二次是解码器报错。模型调用、跟踪状态、风险处置三处各有什么区别？假设出问题前轨迹已确认且活动中。
2. 你看到原录像里有一只飞鸟，告警列表里却没有。要区分“算法没采到”“模型采到了但没检出”“后端没有处理”，你会按什么顺序找哪几份证据？哪些结论可能因缺证据而无法下？
3. 转发队列从 512 调到 8192 能改善本例花屏，同时算法只取最新帧会跳过画面。这两个决定为什么不矛盾？65.296 秒实验里的 1,338 应当怎么解释？

<details>
<summary>回答后展开核对</summary>

1. 清晰空帧执行了一次推理，跟踪器收到有效空检测，已有轨迹可以暂失，后来有足够证据才可判定风险解除。解码异常发生在推理之前，这次没有新的目标观测，任务收尾把已有活动轨迹标为中断。现场牛是否离开仍然未知。
2. 原录像先定位经过时段；再查同摄像头、同会话的已保留检测采样和时间戳，检查对应处理帧里鸟是否可见、输出过哪些类别或框。项目没有单独的飞鸟类别。若有轨迹消息，再按消息 ID 查待发、后端接收或拒绝记录，最后查规则是否生成风险。没有采样录像可能只是归档未触发、限频或受限；没有业务告警也不能单独证明模型漏检。
3. 解码前缓冲突发的压缩数据，是为了让解码器拿到可用码流。解码后选择较新的完整图，是为了避免慢消费者长时间落后。1,338 是探针为新鲜度跳过的已解码帧数，不是损坏包数；它也提示采样覆盖存在间隙。

</details>
