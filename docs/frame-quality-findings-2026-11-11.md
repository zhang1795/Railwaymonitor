# 算法输入花屏排查

## 证据与原因

用户提供的第二张图片（`kite 0.73`）与业务证据文件 `31e276eed05bf9a0621563266b4ecfae5a936baea1a7f9153ddb7dace5c96b50.jpg` 一致。数据库采集时间为 UTC 2026-11-11 04:13:56.642（北京时间 12:13:56），早于当天 12:52 的媒体队列修复。第一张图片未作唯一匹配，不能据此推定其采集时段。

完整的故障链为：高码率 H.264 源经转发时，原 512 写队列容纳不下突发大关键帧；接收端得到损坏码流；解码器可能隐藏错误并输出非空的补偿画面；旧代码将 `ret=True` 视为可推理，原生错误日志又被丢弃，最终将花屏作为正常画面识别并保存截图。JPEG 文件校验通过只说明截图字节一致，不能证明其上游 H.264 帧正确。

队列对照实验保持 MediaMTX 1.18.2 与源文件不变，512 时复现，8192 时未复现。更换转发器/FFmpeg 版本、调包大小没有消除原问题。8192 已部署；原始用户视频和损坏历史证据均保留。

## 此次补齐的检查

RTSP 使用 PyAV 12.3.0 严格解码：TCP、启动等待完整关键帧、坏包/坏帧标志、原生 ERROR 日志与解码异常检查。出现损坏立即终止该次输入，不能产生一帧“空目标”。工作任务以 `INTERRUPTED` 结束，后端重新协调会话；不能把源异常判断为风险解除。前端展示解码异常并清除旧预览。

解码在独立可终止进程内进行，4 个解码线程，最新帧队列有界。慢推理跳过旧帧；解码自身相对 PTS 的积压增长超过 2 秒则中断重连。这个指标衡量本次解码积压变化，不代表经过硬件校准的摄像头端到端时延。父进程死亡时，Linux 子解码进程随之退出。

这是一道码流完整性检查，不能证明画面语义正确，也不能识别摄像头已经编码进去的污损/遮挡/传感器坏画面。未使用简单清晰度阈值过滤真实风险图像，未修改模型置信度来掩盖花屏。

## 已完成的本机验证

- 原文件全片 373 帧通过；已知损坏录像先交付 71 帧正常画面，再拒绝损坏码流。
- 当前源原 OpenCV 连续解码 65 秒，共 1507 帧；抽查 62 帧与原文件参考帧像素一致。
- 新解码当前 4K 源 65.296 秒共解码 1535 帧；慢消费者读取 197 帧，跳过 1338 帧；抽查 50 帧与原文件参考帧像素一致。相对解码积压增长最大 42.707 ms，末次 0 ms，没有解码错误。
- 93 项算法侧测试、5 项网关测试、13 项部署测试通过；后端 H2 95 项、隔离 MySQL 95 项通过；前端 56 项和类型/生产构建通过。

抽查不是逐帧全时段保证。原始录像独立保存，历史坏证据不会因修复而变正确，需要人工复核。隔离完整链路验收、两批发布和后续三路4K检查均已完成，见[最终实施报告](frame-quality-and-detection-views-results-2026-11-11.md)。
