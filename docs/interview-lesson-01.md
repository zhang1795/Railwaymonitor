# 第一课 · 摄像头连续拍到一头牛，系统得到了几个结果？

需要一张纸，约 25 分钟。学完后，你应该能向没做过视觉项目的人解释模型从一张图里读出什么，跟踪器多做了哪一步，以及业务后端凭什么产生风险告警。

## 先把一段视频暂停（5 分钟）

想象铁路旁有一台固定摄像头。把视频停在一头牛刚出现在草坡上的那一刻。暂停后看到的这一张图，就叫作**一帧**。在纸上画一个代表画面的长方形，在左侧画一个小长方形代表牛所在的位置。横坐标从左往右增大，纵坐标从上往下增大。

算法把这张图送入已经训练好的模型，这次计算叫**推理**。假设它给出下面三个值。数字为教学示例，你可以在纸上改动它们。

| 项目里的名称 | 示例 | 这句话在说什么 |
| --- | --- | --- |
| `class_name`（类别） | `cow` | 模型认为框中的对象是牛。 |
| `bbox`（检测框） | (100, 60, 180, 140) | 左上角在 (100, 60)，右下角在 (180, 140)。这次预测落在哪个位置，可以直接画回原图。 |
| `confidence`（置信度） | 0.84 | 模型给本次检测的分数。项目用分数筛选候选结果。单个框的分数无法告诉我们模型在铁路现场的整体准确率。 |

**停下来做一题。** 只看这三个值，写出一个你已经知道的事实，以及一个还无法判断的事情。可以写“模型在画面左侧框出一头牛”，但“它已经在危险区域停了十秒”需要位置规则和前后多次观测。

事实：当前帧中，检测到了cow这一异常目标，并包括其位置和置信度。 无法判断的事情：这个cow异常目标累计出现的时长

## 再放四张图（7 分钟）

假设这是一次新检测会话，下面是算法实际处理的五帧。每帧只有一个通过筛选的牛框，牛缓慢向右走。摄像头可能还输出过其他画面，这里只数实际送去推理的帧。用铅笔把你认为属于同一头牛的框连起来。

| 处理顺序 | 牛框的横向范围 | 模型这一帧检出几个框 | 累计输出过几条不同的确认轨迹 |
| --- | --- | --- | --- |
| 1 | 100～180 | 1 | 先自己填 |
| 2 | 104～184 | 1 | |
| 3 | 108～188 | 1 | |
| 4 | 112～192 | 1 | |
| 5 | 116～196 | 1 | |

你画的那条线就在做**跨帧关联**。项目里的 SORT 跟踪器先估计已有目标会移动到哪里，再将新框与预测位置配对。配上后，程序可以继续沿用这条轨迹的编号，叫作 `track_id`。编号属于本次跟踪任务。摄像头重新开始一次会话后，编号可能从头使用。

**核对最后一列。** 假设时间间隔短、每次都匹配成功，按运行入口的五次连续命中设置，依次填 **0、0、0、0、1**。第一次检出就可以在内部建立候选轨迹，到第五次才作为确认轨迹输出。此时共检出了 **5 个框**，输出过 **1 条不同的确认轨迹**。第六帧若又顺利匹配，累计框数变成 6，确认轨迹的不同编号仍只有 1 个。真实运行中，两头牛交叉或被遮挡时，匹配可能出错。第 3 轮会专门练这一点。

## 加一条铁路巡检规则（5 分钟）

在纸上把画面右半边圈出来，把它当成配置好的风险区域。这个例子假设规则只关心进入该区域的牛，要求分数达标，并有连续有效的观测支持停留满 2 秒。

**先判断刚才那五帧。** 如果牛始终在圈外，五次都得高分，并且已经确认是同一条轨迹，能否触发这条规则？答案是 **0 个风险事件**。模型解决了“图里像什么、在哪里”，跟踪器把多次看到的框联系起来，后端还要判断这串观测是否符合配置的规则。

接着假设牛进入右半边。后端在有效观测中检查牛框底边的中心点是否在区域内。该点可以近似代表牛站在画面里的位置。观测持续满足规则后，后端新建一个**风险事件**，并产生一次**首次提醒**。事件记录“这一处风险发生并持续”，提醒记录“在某个时刻提示值守人员”。同一风险持续存在时可以再次提醒，事件仍然是同一个。第 4 轮再数一分钟的例子。

回到真实项目，现场规则需要配置。默认策略会保存待核验观察，也可以产生首次站内观察提示。面试时说“看到了牛”要保留这层区别，具体是哪类提醒取决于当时启用的规则。

## 到项目里找刚才画过的东西（5 分钟）

打开 [detections.py](../RailwayDetector/detections.py)，看 `Detection` 和 `TrackResult` 两个定义。可以把 `class` 理解为给“一条记录有哪些栏”起名。先在两份定义里找你读过的框、类别和分数，再找 `track_id` 出现在哪份里。看到 `detection_index` 时，把它理解为“本帧中这一条检测的位置编号”，它只在帧内有意义。

接着看 [model_init.py 中的 process_frame](../RailwayDetector/model_init.py)。下面摘出其中两行，省略中间的任务取消检查。

```python
records = (detector or _default).detect(frame, stop_event)
return records, tracker.update_detections(records, timestamp=observed_at)
```

第一行，右边的 `detect` 接收一张图，等号把它返回的检测列表取名为 `records`。第二行把这个列表交给跟踪器，`return` 将两份结果一起交还给调用方。哪怕这一帧只有一头牛，前几次也可能出现 **检测列表有一项，确认轨迹列表为空**。上面五行表格里的前四行就是实例。

最后口述一次分工。算法端负责读图、检测、跟踪，并把确认轨迹的观测组织成消息。MQTT 把这些消息送往后端。后端处理风险规则、事件与提醒，值守人员在页面上查看和处置。第 5 轮再讨论消息在路上出故障怎么办。

## 合上文档，试着讲（3 分钟）

1. 同一头牛在五帧里各产生一个框，第一帧有框却没有输出确认轨迹。你怎样向同事解释？
2. 一头牛已经跟踪了很久，始终在已配置风险区域外。单靠把模型分数从 0.84 改到 0.98，这条区域规则能触发吗？为什么？
3. 换成一头牛连续匹配三帧就离开，从新会话开始计。这三帧一共有几个检测框、输出过几条确认轨迹？和五帧的例子相比，哪个数字先变了？

第一题说到“单帧检出”和“连续匹配后确认”就够。第二题应说出区域条件仍未满足。第三题应数出 3 个框、0 条已确认轨迹。能解释自己为什么这样数，就可以开始[第二课《一张图里的牛，怎样变成原图上的检测框？》](interview-lesson-02.md)。
