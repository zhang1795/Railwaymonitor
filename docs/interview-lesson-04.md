# 第四课 · 同一头牛在危险区域里停留一分钟，会告警几次？

第三课结束时，算法已经把连续几帧里的牛接成了轨迹 1。本课从后端收到这条轨迹的第一条确认观测开始。准备一张纸，左列记“风险事件数”，右列记“站内提醒数”。同一头牛的这两列数字会在不同时间增加。

第一遍约 20 分钟，走完第 1～4 节，把一分钟的账算清。第二遍约 20 分钟，做第 5～7 节，给同一案例加上遮挡、换号、错误消息和人工处理。文中的牛和秒数是教学输入，代码和测试入口都来自当前项目。

## 1. 把面试官的“几次”说清楚

假设值守人员打开一条风险记录，发现它从 10:00 持续到 10:01。系统可以在同一条记录下提醒他两次。若面试官问“告警几次”，可以先说“我分别数风险事件和站内提醒，时间从首次确认风险开始算”。这里还有第三种数量，来自算法上报的轨迹观测。

| 数的是什么 | 一头牛持续出现时会怎样 | 认哪个编号 |
| --- | --- | --- |
| 轨迹观测消息 | 算法会多次报告最近一次观测。持续可见时通常约每秒一条快照，状态或类别变化也可触发上报。 | `eventId` 标记一条消息，重发沿用原 ID。同一来源轨迹内，`sequence` 表示先后次序。 |
| 业务风险事件 | 同一段已成立且持续的风险，一直更新同一条记录。 | `alarm_id` 标记这段事件。轨迹的来源身份还包含节点、摄像头、会话及 `trackId`。 |
| 站内提醒 | 新建事件可有首次提醒，持续风险可以再次提醒。 | 每次提醒有自己的 `notice_id`，归属同一个 `alarm_id`。 |

**最短答案。** 假设首次判定时新建风险事件、提醒间隔 60 秒，牛持续满足规则，实时观测一直有效，无升级、解除或重新进入。从风险成立起的前 60 秒（含起点，不含第 60 秒）共有 **1 个风险事件、1 条首次提醒**。到第 60 秒或之后的首条符合条件的新观测，仍然是 **1 个事件，累计 2 条提醒**。下面沿代码找出这两个数字的来历。[算法快照 TrackEvents](../RailwayDetector/track_events.py) · [后端聚合 RiskIncidentService](../web-springboot/src/main/java/com/example/detection/RiskIncidentService.java)

## 2. 一条牛的观测，凭什么算进危险区域？

假设现场人员已启用一条规则，关注牛（类别编号 2），当前分数至少 0.50，危险区域取画面的右下侧矩形 `[0.50, 0.40, 0.90, 0.90]`，停留 2 秒，缺失容忍 3 秒，提醒间隔 60 秒。为方便计数，本例关闭升级。项目会为检测会话保存规则快照，后续处理同一会话时沿用这套尺度。[规则快照 RiskPolicyService.capture](../web-springboot/src/main/java/com/example/detection/RiskPolicyService.java)

**先做一道位置题。** 原图宽 640、高 480，牛框为 `[300, 100, 420, 336]`。它的左边缘在画面左半边，身体的一部分伸进了危险区。项目取框底边中心点近似表示落脚位置。逐步算：

1. 原图上底边中心是 `((300 + 420) / 2, 336) = (360, 336)`。
2. 横坐标除以图宽、纵坐标除以图高，得到 `(0.5625, 0.70)`。这叫**归一化坐标**。同一画面等比缩小后仍可使用同一个区域配置。
3. 0.5625 落在 0.50～0.90，0.70 落在 0.40～0.90，故落点在区域内。若当前类别是牛且分数为 0.84，这条观测通过单次筛选。边界上的点也算在内。

代码中的 `b.get(0)` 和 `b.get(2)` 分别取左、右边界，`b.get(3)` 取底边。下面是项目实际使用的计算。[RiskPolicy.qualifies](../web-springboot/src/main/java/com/example/detection/RiskPolicy.java)

```java
double footX=(b.get(0).asDouble()+b.get(2).asDouble())/2/width,footY=b.get(3).asDouble()/height;
```

**改一个输入。** 位置和类别都不动，把当前分数降到 0.42，即使这头牛先前最高曾达到 0.98，本次也通不过 0.50。历史最高分可以供人复核，累积停留用的是当前观测。若摄像头根本没有启用风险规则，默认保存的是 **OBSERVATION（待核验观察）**，新建时也有一条站内首次观察提示。看到提醒后，还要看记录种类才能知道系统是否判定了风险。

## 3. 从第一次达标到创建风险，代码记住了哪个时刻？

在纸上写四个字段。`lastSeen` 是最近实际看见目标的观测时刻，`qualifying_since` 是本轮连续达标从何时开始，`risk_since` 是业务确认这段风险的时刻，`observedThrough` 是有效观测推进到何时。看见牛时后者通常和 `lastSeen` 相同。画面清晰但没再见到牛时，两者会分开。另有 `firstSeen` 记录算法首次输出这条确认轨迹的时刻，可能早于入区。

现在设 `t=0` 是起点，**轨迹已经过第三课的五次命中确认**。每秒有一条新鲜的区域内有效快照，当前分数都是 0.84。

| 实际经过时间 | 后端在纸上做的计算 | 风险事件数 | 站内提醒数 |
| --- | --- | ---: | ---: |
| t=0 | 首次达标，记下起点 0。停留 0 秒。 | 0 | 0 |
| t=1 | 同类、相邻上报间隔 1 秒，继续从 0 计。 | 0 | 0 |
| t=2 | 2 − 0 = 2，达到停留要求。新建事件，`risk_since=2`，写入 `FIRST`。 | 1 | 1 |
| t=3～61 | 一直更新原事件。到 t=61，风险已成立 59 秒。 | 1 | 1 |
| t=62 | 62 − 2 = 60，进入第一个持续提醒区间，写入 `ONGOING`。 | 1 | 2 |
| t=63 | 仍在刚才的提醒区间，已有该条提醒。 | 1 | 2 |

沿 `RiskIncidentService.apply` 对照。下面四句摘自同一方法，按执行顺序列出，中间略去分支。Java 中 `&&` 表示条件须同时成立，`||` 表示任一成立即可。[apply 与 create](../web-springboot/src/main/java/com/example/detection/RiskIncidentService.java)

```java
boolean validInside=raw.equals("ACTIVE") && (!policy.enabled() || policy.qualifies(e));
// 当 validInside 为真时，先结合上一条快照算出 continued
if(!continued || qualifying==null)qualifying=seen;
// 不满足 validInside 的分支会清空 qualifying
boolean qualified=validInside && (!policy.enabled() || elapsed(qualifying,seen,policy.dwellSeconds()));
// 在 create 内，用新生成的事件编号写首次提醒
notice(id,"FIRST",0,at);
```

1. **这一条是否达标？** 在本例已启用规则的前提下，需要 `ACTIVE`、牛、分数足够和落点入区。此时还没有检查 2 秒停留。
2. **能否沿用上一个起点？** 上一条也须为 `ACTIVE`、通过规则、类别相同，且两条的 `lastSeen` 间隔不超过配置的 3 秒。若换成 t=0 和 t=4 才各收到一条达标观测，第二条会从 4 重新计时。两端都有牛框，中间这四秒却缺乏足够连续的观测。
3. **停留是否足够？** 用当前观测时间减连续达标起点。插入一条低分或 `MISSING` 观测会打断连续证据。多发十条相同的重试消息也不能把 1 秒变成 2 秒。
4. **这条来源已有事件吗？** 有仍在持续的事件时，更新它。没有关联事件或旧事件已关闭时，先查有没有可接续的业务事件。找不到合适的旧事件才创建；首次提醒写在创建路径里。第 6 节会实际走一次查找。

## 4. 第 60 秒的提醒是谁触发的？为什么第 61 秒不会再多一条？

假设把表中的 t=2 重新记作“风险年龄 0 秒”。代码用整数除法把风险年龄分段，项目把这个段号叫 `bucket`，可以读作“第几个提醒区间”。以下三句发生在收到一条**新的、仍然合格且新鲜的直播观测**时。[持续提醒判断](../web-springboot/src/main/java/com/example/detection/RiskIncidentService.java)

```java
long bucket=Math.max(0,Duration.between(riskSince,seen).getSeconds()/policy.reminderSeconds());
if(newLevel>oldLevel)notice(alarm,"ESCALATION",newLevel,observed);
else if(bucket>0)notice(alarm,"ONGOING",bucket,observed);
```

**第一步，算段号。** 风险年龄 59 秒时 `59 / 60 = 0`（整数除法），60 秒和 61 秒都在第 1 段，120 秒进入第 2 段。如果第 60 秒没有新快照，但第 61 秒到了符合条件的快照，就在第 61 秒评估。旧消息补传或回放时间轴不能据此补发一串历史持续提醒。

**第二步，决定提醒种类。** 当前观测引起风险等级上升时，先写 `ESCALATION`，以新等级区分升级提醒。否则段号大于零时，才尝试写普通持续提醒。这里的优先级只针对**当前这次处理**。如果下一条合格观测仍在同一段，而这段尚无 `ONGOING`，仍可能产生持续提醒。

**第三步，让数据库记住已经发过哪一种提醒。** 假设事件编号是 37，则首次提醒的键是 `(37, FIRST, 0)`。第一次跨过 60 秒时，新键为 `(37, ONGOING, 1)`。下一秒即使由另一条全新的消息触发，仍会尝试写相同的键。表上有 `UNIQUE(alarm_id, kind, bucket)`，代码用 `INSERT IGNORE`，只在真正插入新行后才继续安排外部通知。重复传输一条旧消息，和多条新观测落进同一提醒区间，是两个不同的问题。[提醒表与已读回执的键](../web-springboot/src/main/resources/db/p1-alarm-migration.sql)

<details>
<summary>进阶追问 · 回放、断网重放、已读和短信分别有什么影响？</summary>

- 持续或升级提醒的当前 V4 分支要求规则启用、当前观测已满足停留、会话未中断、事件未删除、时间来源是直播接收时间 `received_at`。它还用秒级约 15 秒的条件检查处理时间离现在有多远，以及最近看见目标到处理之间的延迟。过旧的数据仍可能留下历史事件或首次观察提示。
- 某一段完全没有合格观测时，仅靠时间流逝不会新增持续提醒。恢复后只检查当前段，代码没有遍历错过的每一个区间。
- 人工已处理是操作员对事件的处置，已读是某账户对某条具体提醒的回执。风险仍持续时，新提醒有新编号，可以继续显示未读；此前填写的处置结果会保留。
- 上面数的是站内提醒。外部发送还受事件种类、渠道配置和等级条件约束。当前短信发送条件排除了普通 `ONGOING`，所以“站内有两条”不能直接换算成“两条短信”。[NotificationOutbox](../web-springboot/src/main/java/com/example/detection/NotificationOutbox.java)

</details>

## 5. 画面里牛消失了、牛走出区域了、摄像头断了，如何区分？

先固定为单一来源轨迹且原事件已经成立。把“这条观测是什么”和“后端认为这段风险怎样了”画成两列。

| 输入给后端的证据 | 业务状态怎么变化 | 为什么 |
| --- | --- | --- |
| 清晰画面暂时没匹配到牛，算法发 `MISSING` | `PRESENT → MISSING` | 暂失保留原记录。之后重新获得满足规则的观测，可以回到 `PRESENT`。配置了停留时间时，需要重新积累达标证据。 |
| 牛仍被跟踪，算法继续发 `ACTIVE`，但脚点一直在区域外 | 先 `MISSING`，有效区域外观测跨度达到容忍时间后可转 `CLEARED` | 跟踪编号可以一直不变；牛所在的位置已不再构成这条区域风险。后来再次入区并满足停留条件，可以形成新的风险事件。 |
| 算法发出 `ENDED / confirmed_absence`，且缺失证据区间通过校验 | `CLEARED` | 接收端会检查 `observedThrough − missingSince` 是否够长。算法端在结束前还检查同类重叠检测造成的身份疑点。 |
| 视频源报错、停监测或身份存疑而中断 | `INTERRUPTED` | 记录说明观测中断，此时无法确认牛已离开。只有沉默而无新观测，也不能仅靠墙上时钟判定安全。 |

如果同一个业务事件已经关联两条来源轨迹，旧轨迹报结束时后端还会看另一条是否近期仍有达标观测。若有，事件可继续保持 `PRESENT`。这解释了为什么一个轨迹的结束与整个事件的解除有时不在同一时刻。[状态切换与 otherPresent](../web-springboot/src/main/java/com/example/detection/RiskIncidentService.java)

## 6. 从轨迹 1 跳到轨迹 2，还能合成原事件吗？

设遮挡前业务事件 A 已存在，来源是轨迹 1。遮挡后，算法上报了新编号 2。下面从**新来源已满足风险条件**的时刻开始，逐步执行 `candidates`。项目里的实现给了我们一个回答“依据错误还能正确聚合吗”的具体例子。[candidates 与 iou](../web-springboot/src/main/java/com/example/detection/RiskIncidentService.java)

1. **先缩小范围。** 从同一摄像头、同一检测会话、同一类别、未删除且业务状态为 `MISSING` 的旧事件里找候选。另一台相机或上一次任务里的 1 号轨迹都不会被拿来延续这里的风险身份。
2. **查看原来的来源是否近期还可见。** 旧事件若有其他证据表明其来源近期仍为 `ACTIVE`，排除该候选。例子是原牛刚走到区域外，后端业务状态已是 `MISSING`，但算法仍清楚看见它。附近又走进一头牛时，贸然合并会把两头牛算成一头。
3. **比较时间和位置。** 从候选事件最后的区域内时间 `last_inside` 到新来源达标时刻，间隔要在容忍期以内。新旧框各自除以对应帧宽高后比较，IoU 至少 0.3 才留下。若新轨迹确认和停留判定花了太久，即使实际是同一头牛，也可能错过这个窗口。
4. **数候选。** 恰好一个就关联原事件，记作 `RELINKED`。没有候选就新建，记 `NEW`。多个候选都说得通，就新建并注明 `AMBIGUOUS_NEW`。这条路径优先避免把不同对象强行合并，代价是在含糊场景里可能把一段物理风险拆为多个业务事件。

还有一个更难的反例。若算法把另一头牛错接到了**同一个**轨迹编号，类别、位置和时间又全都合理，后端甚至可能没有理由进入“找新来源候选”这条分支。查明这种错配要回到第三课，看当时实际处理的帧、框和身份标注。

**面试官若说“聚合信息有错”，可以请他举例，也可以自己分成以下情况回答。**

| 具体错误 | 项目实际能做什么 |
| --- | --- |
| 编号说是牛，类别名却写成工人；框越界；会话归属错误 | 接收端校验失败，记录拒绝原因，保护现有风险状态。 |
| 同一条消息被网络重发 | 同节点、同消息 ID 且正文摘要一致，返回已记录的处理结果。若 ID 相同但正文改变，按冲突拒绝。 |
| 同一来源的旧序号晚到 | 留下接收记录并忽略旧状态。首次收到的就是缺失或终态且证据不足时，当前 V4 路径保留待核验观察，不能凭累计次数倒推出历史停留。 |
| 规则本身把草地划成轨道，或模型高分误识别 | 这类输入可能通过格式校验。可查本次会话的规则快照、框及图像证据定位原因，需要人工核验或校准。 |

接收端把校验后的风险更新、提醒与消息接收记录放在同一个事务里。同一会话加行锁，按顺序处理竞争更新。第五课再沿这段事务看“已写入，但确认回执丢失”如何恢复。[DetectionIngestService.receive](../web-springboot/src/main/java/com/example/detection/DetectionIngestService.java)

**一分钟口述练习。** “算法负责把已确认轨迹上报为观测。后端按这次会话的规则检查类别、当前分数和落点，连续达标够久才判定风险。同一风险保持一条事件记录，首次和持续提醒分别计数。例如提醒间隔 60 秒，从新风险成立起算，前 60 秒有一次首次提醒，跨过边界且还有新鲜合格观测时，再加一条持续提醒。如果断流，只能标记监测中断。轨迹换号时会按同摄像头、同会话、类别、时间和位置查候选，有歧义就单独留记录。”

**合上文档，做三道题。**

1. 已确认轨迹在第 0、1 秒达标，第 2 秒分数降到 0.42，第 3 秒起每秒重新达标。规则与主例相同。首次风险在第几秒成立？第一条持续提醒最早在第几秒出现？假设无升级且一直有新鲜有效观测。
2. 同一事件从风险成立起已有持续 59 秒的合格观测，此时摄像头断流，此后 20 秒没有新观测。期间会增加几条持续提醒？能判断牛已经离开吗？如果操作员之前已读，哪一项结论会变化？
3. 原轨迹暂失，新编号已满足风险条件。若通过所有筛选的旧事件分别有 1 个、2 个，后端各怎么做？如果上游根本没有换号，只是把两个相似目标接错了，后端凭什么能发现，或者为什么发现不了？

<details>
<summary>完成后展开答案</summary>

1. 第 2 秒的低分打断连续证据，第 3 秒重新计时，第 5 秒满足 2 秒停留并新建风险。提醒时钟从第 5 秒开始，第 65 秒的合格观测才进入第一个持续提醒区间。
2. 期间增加 0 条持续提醒。没有新鲜合格观测来触发提醒，断流也无法证明目标离开。已读仅改变该账户对原提醒的回执，两项结论都不变。
3. 唯一候选关联原事件，两个候选则新建并记录歧义。上游若沿用原编号且各字段自洽，后端可能完全发现不了，需要用对应帧、轨迹和人工证据复核。

</details>
